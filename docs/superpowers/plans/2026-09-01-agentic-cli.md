# Agentic RL CLI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Evolve exterm from isolated train/steer commands into one persistent, coding-agent-style RL workspace with safe-point steering, bounded project editing, and a bundled domain MCP server.

**Architecture:** Reuse the existing `TrainerApiClient`, `TrainerWebSocketClient`, `TerminalRenderer`, FastAPI trainer, checkpoint system, and LangGraph steering graph. Add a CLI session/event loop above them, a trainer-side bounded steering queue whose callback owns safe-point transitions, and a small tool registry shared by the in-process agent and stdio MCP adapter. Keep the trainer as the only owner of model/code application and the dashboard as another client of the same event stream.

**Tech Stack:** Node 18+, TypeScript, Commander, Node `readline`, existing `ws` and `picocolors`, Python 3.10+, FastAPI, Pydantic, Stable-Baselines3, existing LangGraph/Ollama integration, MCP stdio transport, pytest, Node test runner or the existing test stack.

**Spec:** `docs/PRD-agentic-cli.md`, with baseline compatibility requirements in `PRD.md`.

## Global Constraints

- The CLI must remain local-first and preserve the existing direct commands.
- No generic model shell tool is available in v1.
- No code edit may be applied without a pre-edit checkpoint.
- Runtime edits execute only at a trainer safe point after the current callback invocation completes.
- High-risk changes require an explicit approval command.
- The dashboard remains a client of trainer APIs; it does not gain a second state machine.
- Bundled MCP tools call existing domain services rather than duplicating trainer logic.
- Use existing dependencies first; add only the MCP package required for a standards-compliant stdio server.
- Every non-trivial parser, queue, or safety boundary gets one focused automated test.

## Existing seams to preserve

- `packages/cli/src/client/api.ts` already owns authenticated HTTP calls.
- `packages/cli/src/client/ws.ts` already owns authenticated trainer WebSocket messages.
- `packages/cli/src/ui/terminal.ts` already renders telemetry but assumes exclusive stdout ownership.
- `packages/cli/src/commands/train.ts` currently combines connection, rendering, readline, and lifecycle and should be reduced to an adapter over the new session runtime.
- `trainer/exterm_trainer/engine/callbacks.py` is the only safe place to observe completed training steps.
- `trainer/exterm_trainer/engine/runner.py` owns model, environment, checkpoint, and video state.
- `trainer/exterm_trainer/server.py` owns HTTP/WS transport and audit logging.
- `trainer/exterm_trainer/agent/graph.py` already generates steering code and should be wrapped before it is expanded.

- [ ] **Step 1: Write the queue and safe-point tests**

    request = QueueSteerRequest(request_id="r1", instruction="penalize jerky actions", requested_at_timestep=6600)
    assert runner.queue_steering(request).state == "queued"
    assert runner.process_safe_point() == []
    runner.mark_callback_complete(6700)
    result = runner.process_safe_point()
    assert result[0].safe_point_timestep == 6700

- [ ] **Step 3: Implement the bounded queue**

Use `queue.Queue(maxsize=20)` or a lock-protected deque, reject overflow with HTTP 429, assign request IDs server-side when absent, preserve FIFO order, and coalesce only exact duplicate pending instructions. Never call the LLM or write files from the callback thread.

- [ ] **Step 4: Process one request at a completed-step boundary**

- [ ] **Step 5: Add endpoints and WS events**

## Ponytail decisions

- Reuse existing HTTP/WS clients, trainer, checkpoint system, and LangGraph agent; do not introduce a second orchestration backend.
- Use Node `readline` and ANSI primitives before adding a terminal UI framework.
- Bundle only the exterm MCP server. GitHub MCP remains optional because repo hosting is not needed to train or steer an RL run.
- Keep the agent tool set bounded and omit shell execution; add it only after a separate security review demonstrates a real need.
- Use a bounded in-memory queue for v1. Add persistent queue recovery only if users demonstrate that process restarts during training are a required workflow.
